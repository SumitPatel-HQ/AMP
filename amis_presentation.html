AMIS · Internal presentation

Adaptive mission planning, demonstrated end to end.

A local simulator that plans which Earth photos a satellite should take, deliberately breaks the plan, fixes it, and explains the fix.

Decision support for mission planning Not satellite control

AMIS never commands a spacecraft. It is a research simulator and planning workbench: define a mission, schedule observations under real timing and resource limits, inject a controlled disruption, rebuild the remaining plan, and inspect exactly what changed and why. That distinction matters to everything that follows.

02 — The problemMore wanted than a satellite can do.

One satellite, one day, many photo requests. Each target is only visible in short spans, each shot has a deadline and costs power and storage, and conditions change mid-mission. The planner must pick a feasible subset — then keep it feasible when reality intrudes.

The squeeze, visualised
Timing pressure
  • Narrow visibility spans per target
  • Hard deadlines per request
  • No two shots at once
Resource pressure
  • Battery per shot, floor at zero
  • Storage per shot, cap at capacity
  • Satellite must be available
Live pressure
  • Clouds kill optical chances · batteries sag · urgent requests arrive mid-mission
  • Past work cannot be rewritten — started actions are frozen

04 — Research foundationReal literature, not decoration.

Seven themes from the project specs. No invented papers — each theme maps to a design choice in AMIS.

Satellite scheduling

Imaging tasks under windows, deadlines, power and memory are a studied hard optimisation problem — NP-hard in the agile case. → Why AMIS pairs a fast baseline with a bounded optimiser instead of claiming optimality.

Dynamic scheduling

Tasks arrive over time with deadlines and stability matters. → Emergency arrivals plus frozen past plus a stability rule.

Cloud-aware scheduling

Optical takes fail under cloud: ~35% of Landsat-7, ~80% of SPOT lost in cited studies. → CLOUD_BLOCK as a first-class event, not an edge case.

Autonomous planning · CASPER

NASA JPL’s Continuous Activity Scheduling, Planning, Execution and Replanning: keep planning during execution and repair conflicts as they appear. → The plan → execute → impact → replan loop.

Flight proof · EO-1 ASE

The Autonomous Sciencecraft Experiment flew onboard EO-1 from 2004: science analysis, CASPER planner, robust execution — and cut operations cost. → Evidence autonomy works in space; AMIS replays it as a ground simulator.

Perturbation handling

Adapt a plan while minimising disruption to the original. → Churn metric plus previous-window-first stability.

Agile EO scheduling

VTW (visible span) vs OTW (shot inside it), slew-dependent transitions, oversubscribed targets. → Window/action split, settling gap, culmination option; benchmarks frame greedy as baseline with headroom.

Standards and engines used as-is, with links: Skyfield · SGP4 (sgp4 package) · CelesTrak (OMM element sets) · OR-Tools CP-SAT. CCSDS OMM is the stored element format.

08 — Planning engineOne contract, two implementations.

Planner protocol

plan(scenario, state, requests, windows, previous_plan) → MissionPlan

Knows nothing of FastAPI, React, or Postgres. Same call plans and replans.

GreedyPlanner — the baseline
  • Sort: priority ↓, deadline ↑, duration ↑, id ↑ — ties never random
  • Try window start, peak-centred start, then after each placed action
  • First fully-feasible slot wins, else unscheduled with reason
  • Deterministic, millisecond, explainable step by step
CP-SAT planner — the challenger
  • OR-Tools constraint model: integer seconds, optional intervals, no-overlap, linear resource sums
  • Maximises priority sum + small stability term
  • Bounded deterministic search; records status, bound, optimality gap
  • Never worse than greedy — falls back to it
Why both exist

Greedy is the honest, fast, explainable floor. CP-SAT measures how much value the floor leaves behind on tight problems. Same protocol means the comparison is fair — and benchmarks show a real gap (priority-greedy ≈ half of optimal on small cases).

09 — Constraint engineSix gates, one vocabulary.

1 · Containment

action inside its window

2 · Deadline

ends before request deadline

3 · No overlap

plus settling gap between shots

4 · Battery

projected in time order, floor 0

5 · Storage

projected in time order, cap respected

6 · Availability

satellite on, outside outage spans

Failure path — always the same

Constraint failure → ReasonCode → sentence. The code is the source of truth and is testable; the human text is generated from a template afterward. No LLM plans, ever.

Key codes: WINDOW_INVALIDATED · INSUFFICIENT_BATTERY · INSUFFICIENT_STORAGE · DEADLINE_VIOLATION · TIME_OVERLAP · SATELLITE_UNAVAILABLE · NO_OBSERVATION_WINDOW · NO_ALTERNATIVE_WINDOW. Full vocabulary lives in §19.

13 — Plan diffEvery request gets a verdict.

UNCHANGED

Same window, same start. The quiet majority — stability made visible.

MOVED

Same request, new time/window. Demo: OBS-B 10:20 → 11:15.

INSERTED

New in v2 — e.g. an emergency arrival accepted.

DROPPED

In v1, infeasible in v2 — with its reason code attached.

COMPLETED

Finished before the replan — frozen history, shown so v2 reads honestly.

17 — Determinism + offlineGuarantees, not footnotes.

Reproduce anything
  • Fixed planner ordering; ties by id
  • CP-SAT: single worker, fixed seed, work-based time limit
  • Sorted inputs; pinned library versions recorded in outputs
  • Windows rounded inward to whole seconds
Never phone home
  • Offline element snapshots + SHA-256 manifest
  • Committed ephemeris excerpt, hash recorded
  • No live TLE fetch from the server (socket-blocked in tests)
  • Scenario + event log = full replay

Stale-orbit safety: warn beyond 7 days from element epoch, reject beyond 14. Same inputs → same windows → same plans, checkable by an examiner.

19 — Technical depthFor the examiner who pushes.

Main page stays readable; depth lives here, expandable. Nothing below is new — it is the implementation notes, compressed.

+Greedy ordering + stability + candidate starts
  • Order: priority desc → deadline asc → duration asc → id asc. For each request, previous window first while still valid (stability), then earliest start.
  • Starts tried per window: clamped window start, peak-centred start when culmination placement is on, then the instant after each placed action plus settling gap — anything ending past the window is excluded.
  • Checks in order: containment → deadline → availability/outages → projected resources → overlap. First full pass wins; last violation kept for the unscheduled reason.
  • Zero candidate windows → NO_OBSERVATION_WINDOW (first plan) or NO_ALTERNATIVE_WINDOW (lost placement).
+CP-SAT formulation (bounded, deterministic)
  • Integer seconds from mission start; per request-window pair a presence literal + optional fixed-size interval; at most one window per request; one global no-overlap over frozen + optionals.
  • Outages via before/after bools gated on presence. Battery/storage as linear sums under the locked one-way model. Objective: priority sum + small stability term mirroring greedy.
  • Single worker, fixed seed, work-based limit; records status, objective bound, optimality gap; falls back to greedy rather than returning worse. Unscheduled reasons come from re-running the standard checks on the solution.
+Resource projection + frozen + outages
  • Projection walks frozen then placed actions in time order, committing costs — two tasks that fit alone can fail together, and only the walk catches it.
  • Frozen = action.start ≤ now: carried byte-identical, still blocks time, exempt from re-validation, excluded from churn denominator logic.
  • Payload outage toggles availability over an interval; comms outage invalidates overlapping contacts. Both flow through the same impact → replan path.
+Orbital equations actually used
  • Mean altitude from mean motion (Kepler III); off-nadir → elevation threshold on a spherical Earth; sin(off) = R/(R+h) · cos(elev).
  • At 705 km: 30° → ≈56.3° elevation, ≈415 km offset, ≈120 s overhead; 45° → ≈38.3°, ≈220 s; 0° horizon ≈64° tilt — not imaging.
  • Pair rise/set around culminations incl. windows open at either edge and repeated culminations; sun filter at culmination; round inward; drop shorter-than-duration; per-request numbering; geometry + provenance fields default absent so old serialisations stay identical.
+API routes (groups + exact list)

20 — Limits + futureHonest, then ambitious.

Admitted limits
  • Single satellite; global overlap and one battery
  • Simplified energy (no recharge) and storage (no downlink release) in MVP
  • Fixed costs per request, not derived from power/data-rate × duration
  • Image quality flat with angle unless culmination placement is on
Ordered future (waves)
  • Real-mission builder + Load + Examples + ground track (done per plan)
  • CP-SAT comparison with gap reporting + evaluation suite
  • Payload outages, settling gap, derived costs, culmination option
  • Stations + contacts + downlink + comms outage
  • Archived-weather cloud events · slew + recharge · multi-satellite last

Future work is never presented as implemented. Each wave is independently testable; earlier waves keep passing as later ones land.

21 — Examiner Q&AStory first, proof ready.

+Why a simulator, not real satellite control?
Say: control needs flight software, safety, radios and licences — our research question is planning logic, and a simulator makes it repeatable and checkable.

Backup: PRD §6 out-of-scope list; SRD offline rule; same-seed replay. Proof: run the no-frontend integration test.

+What is novel versus a simple calendar?
Say: windows from physics, six interacting constraints, frozen history, diagnosis before repair, and every change scored for stability and explainability.

Backup: projection walk, stability rule, churn + coverage. Proof: §09/§15 cards.

+Why greedy first, why CP-SAT second?
Say: greedy is the fast explainable floor; CP-SAT measures what the floor leaves behind — fairly, on the same contract.

Backup: fallback guarantee; gap recorded; benchmark headroom (~half of optimal). Proof: §08 + §19.

+Why immutable plans + event log?
Say: audit and repeat — same mission plus same ordered events always reproduces the same versions.

Backup: ADR-0002; parent ids; diffable rerun minus wall-clock. Proof: replay test.

+What is frozen?
Say: started work is history — replans never rewrite it, only rebuild the future around it.

Backup: start ≤ now; byte-identical carry; still blocks time; exempt from validation. Proof: §12 + replan test.

+How is utility calculated?
Say: sum of priorities of scheduled plus completed requests, deduplicated.

Backup: simple, monotone, later weightable by geometry. Proof: metrics module + comparison table.

+What are churn and coverage?
Say: churn = how much of the future moved; coverage = how many moves carry a reason. Demo: 0.25 and 1.0.

Backup: unfrozen-only denominators; stability goal. Proof: §15.

+Why reason codes instead of LLM text?
Say: codes are deterministic and countable; sentences are generated from them. An LLM must never plan.

Backup: fixed vocabulary + templates; coverage gate. Proof: trace builder.

+Why synthetic vs orbital windows?
Say: synthetic tests logic, canonical stages the story, orbital supplies truth — the planner cannot tell which it reads.

Backup: WindowProvider protocol; per-mission policy. Proof: §06–07.

+Why offline snapshots?
Say: catalogue policy, determinism, and audit — fetch rarely as a developer, serve always from committed data.

Backup: 2-hour update cadence; hashes; socket-blocked tests. Proof: §17.

+Why single satellite?
Say: one battery and global overlap keep the MVP honest; constellation assignment is the last wave because it widens every interface.

Backup: per-satellite overlap/resources/tracks planned; request keying preserved. Proof: §20.

+If asked anything unknown?
Say: state what you know in three points, name the file where truth lives, admit the limit plus the next test — then offer to open the code live.

Calm beats long defence. The §19 panels are your safety net.
